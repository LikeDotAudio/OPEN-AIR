# BUG: Race Condition in GUI Builder Causing Partial Render
- **ID**: 20260314_183842
- **STATUS**: RESOLVED
- **SEVERITY**: 1 (Critical)
- **COMPONENT**: `oaGuiBuild.gui_display`

## Issue
The application's GUI was only partially rendering, often appearing as if it had stopped midway through building. This was most noticeable when processing directories without an explicit `layout.json`, where the builder would fall back to its default item-processing logic. The application would incorrectly signal that the build was complete while child components were still being asynchronously processed, leading to an incomplete and non-functional UI.

## Root Cause Analysis
A critical race condition existed in the `_build_from_directory` method within `gui_display.py`. This function is the core of the recursive GUI build process.

1.  When `_build_from_directory` was called for a directory that should be processed by the default "directory listing" logic, it would delegate the work to a helper function, `_process_default_directory_items`.
2.  Crucially, `_build_from_directory` did **not** pass its `on_complete` callback to the helper function. Instead, it called the helper and then immediately called `on_complete` itself.
3.  The `_process_default_directory_items` function works asynchronously, using `self.after()` to iterate through subdirectories and GUI files without blocking the main loop.
4.  Because the `on_complete` callback was fired prematurely by the parent function, the main application logic would proceed as if the build was finished (e.g., triggering state restoration, saving caches). However, the helper function was still in the middle of building the UI in the background. This race condition resulted in the "half-rendered" state reported by the user.

## Resolution
The race condition was resolved by correctly propagating the `on_complete` callback down the execution chain.

1.  The `_build_from_directory` function was modified. When its `layout_type` is `directory_listing`, it now passes its `on_complete` callback directly to the `_process_default_directory_items` helper function.
2.  It no longer calls `on_complete` itself in this branch.
3.  The `_process_default_directory_items` function is now responsible for calling the `on_complete` callback at the very end of its own asynchronous processing loop, specifically after the last item (subdirectory or GUI file) has been processed.

This change ensures that the `on_complete` event is only fired after all asynchronous build tasks for that branch are truly finished, eliminating the race condition and allowing the UI to render completely and reliably. A `try...except` block was also added to ensure `on_complete` is still called even if a catastrophic failure occurs in the main build function, preventing the application from hanging.

## Verification
The application now renders all GUI elements completely and consistently. The issue of the UI build process appearing to "stop" midway through is resolved. The main application window and all its sub-components, including JSON-defined GUIs, are fully drawn as expected.
