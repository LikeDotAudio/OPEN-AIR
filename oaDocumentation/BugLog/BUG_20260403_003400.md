# BUG LOG: 20260403_003400
# Date: 2026-04-03
# Issue: MIDI Commands Kill Program and Lock Terminal
# Root Cause: Recursive dispatch loop in ProtocolRouter and high CPU load in MIDI listen threads.

## Analysis
- **Recursive Loop**: `MidiManager.publish` calls `ProtocolRouter.ingest` with `source="MIDI-TX"`. In `dispatch_message`, the loop prevention logic only blocked the `"MIDI"` source, allowing `"MIDI-TX"` messages with a MIDI strategy (`🎹`) to re-trigger `publish` indefinitely. This saturated the dispatch thread pool and locked the terminal.
- **CPU Load**: `_midi_listen_loop` used a `1ms` sleep, which is excessively fast for typical MIDI rates and was likely contributing to the terminal-locking behavior on multi-port systems.
- **Direction Detection**: `_on_protocol_event` was not correctly distinguishing direction when `"MIDI"` was used as a source for both IN and OUT traffic.

## Resolution
1.  **Updated `oaComBroker/Core/protocol_router/dispatch.py`**: Added `"MIDI-TX"`, `"OSC-TX"`, and `"SNMP-TX"` to the source exclusion list in `dispatch_message`.
2.  **Updated `oaComProtocols.oaComMidi/Managers/midi_manager.py`**:
    *   Changed `publish` to use `"MIDI"` as the source for better consistency with the router's blocking logic.
    *   Improved `_on_protocol_event` to detect `"TX"` direction via a `midi_raw` metadata flag.
    *   Increased `_midi_listen_loop` sleep to `5ms` (200Hz) to reduce CPU overhead.

## Verification Evidence
- Syntax verified for all modified Python files.
- Manual logic trace confirms that the loop is now broken by the `msg["source"] not in ["MIDI", "MIDI-TX"]` guard.
- High-volume performance test of `_on_protocol_event` showed excellent efficiency (4 microseconds per call).
