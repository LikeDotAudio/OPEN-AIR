Bug Report: Recursive Splinker Feedback Loop

Issue

User Complaint: The Splinker works for a second but then enters a feedback loop. Suggestion: add a lock to prevent this feedback. Log Files: Application_20260311_2311.log, Application_20260311_2314.log

Root Cause

  1. Bootstrap Failure: A RuntimeError: cannot set daemon status of active thread in protocol_router.py caused the ThreadPoolExecutor to fail during initialization.
  2. Degraded State: This failure left the system in a partially initialized state where the Protocol Router was inactive, but standard MQTT logic remained active.
  3. Loop Prevention Bypass: Without the Protocol Router's structured metadata enrichment and the Splinker's full management logic, events were bouncing back and forth through the MQTT broker without the splink_active tags, bypassing the initial timestamp-based loop prevention.
  4. Recursive Re-entry: Even when active, a Splink could potentially trigger itself if the transformation (e.g., scaling) resulted in a value change that triggered the same Splink again before the first process completed.

Investigation

  • Logs: Identified BrokenThreadPool: A thread initializer failed in the bootstrap logs.
  • Code Review: Analyzed process_router_event.py and confirmed that while it had timestamp-based caching, it lacked an execution lock to prevent immediate re-entry within the same thread/partition.

Resolution

  1. Core Fix: Resolved the RuntimeError in protocol_router.py to ensure the Protocol Router and its thread pool always start correctly (Fixed in previous task).
  2. Hardening: Implemented Per-Splink Execution Locks using threading.Lock(blocking=False).
    • Each Splink ID now has a dedicated lock in the SplinkerManager.
    • When a trigger matches a Splink, it attempts to acquire the lock. If the lock is already held (meaning that specific Splink is still processing a previous event), the new trigger is skipped.
    • This explicitly breaks recursive feedback loops at the partition boundary.

Verification

  • Test Case: Simulated a high-frequency bidirectional Splink where scaling X -> Y and Y -> X occurred.
  • Result: The execution lock successfully caught the immediate re-trigger, allowing the first transformation to complete and preventing the secondary "echo" from initiating a loop.
