14# **Concept** ** **A **grouper** is an object responsible for aggregating
15# property values. An **actuator grouper** allows control of many actuator
16# objects from a single input value; a **sensor grouper** allows observing many
17# sensor objects via a single output value. Actuator groupers are described
18# below; sensor groupers are TBD. In a working media system, many actuator
19# objects (we will call them **citizens**) will be members of multiple groups.
20# For example, in a multiway stereo sound reinforcement system, the left woofer
21# power amplifier might be controlled by a master gain group, a left-side gain
22# group, and a woofer gain group. To manage the interactions of these multiple
23# memberships, we need a single entity that manages all three of these groups,
24# anticipating the interactions and taking appropriate action. An actuator
25# grouper is such an entity. The grouper:
26#
27# - Registers all the groups and all the citizens.
28#
29# - Remembers which citizens belong to which groups.
30#
31# - Computes new property values when group settings change.
32#
33# - Manages overrange and underrange conditions proactively, so that citizens
34# are never asked to assume out of range values.
35#
36#
37# For any given grouper instance, all of its citizens will all be of the same
38# class. Applications may have a number of grouper instances, one for each
39# citizen class -- an OcaGain grouper, an OcaFrequency grouper, etc. For
40# controlling each group, the grouper creates a proxy object of the same class
41# as its citizens, so that the same controller logic can be used for either a
42# group or an individual worker. It may be helpful to visualize a grouper as a
43# matrix whose rows are groups, columns are citizens, and each cell contains
44# information relating to the membership of the citizen in the group. This
45# information is called the citizen's **enrollment** in the group. **Mechanism**
46# Each Grouper is an instance of this class (**OcaGrouper**). A **group** is a
47# collection of citizens. A citizen that belongs to a group is called a
48# **member** of that group. There is a many-to-many relationship between groups
49# and citizens -- any citizen can be a member of any number of groups. The
50# purpose of the Grouper is to contain the set of groups and the set of
51# citizens, to remember which citizens belong to which groups, and to compute
52# new aggregate values when settings or readings change. The Grouper itself does
53# not provide direct access to parameter data values. That access is provided by
54# **group proxies** or by **peer to peer** mastering -- see below. It is useful
55# to think of a Grouper as a matrix in which groups are rows and citizens are
56# columns. A cell of the matrix is nonempty whenever its column (=citizen)
57# belongs to its row (=group). Such a cell is called an **enrollment.**
58# **Classes of Grouped Objects** Group members can be actuator or sensor
59# objects. A group whose members are actuators is called an **actuator group**.
60# A group whose members are sensors is called a **sensor group**. All the
61# citizens of a given Grouper must be of the same worker class (sounds
62# communistic, doesn't it :) called the **citizen class**. Typically an
63# application will have multiple Groupers, each one supporting a different
64# citizen class. **Adding Groups** New groups can be added to the Grouper at any
65# time, using OcaGrouper's **AddGroup** method. **Group Proxies; Peer to Peer
66# Mastering** Depending on the setting of its **mode** property, a grouper may
67# be in **master-slave mode** or **peer to peer mode. ** In master-slave mode,
68# each time a caller adds a group to a Grouper instance, the Grouper instance
69# creates an object known as a **group proxy.** Thus, there is one group proxy
70# instance per group.** ** The class of the group proxy is the same as the
71# Grouper's citizen class. For example, for a group of OcaGain actuators, the
72# group proxy is an OcaGain object. The purpose of the group proxy is to allow
73# controllers to access the group's setpoint (for actuator groups) or reading
74# (for sensor groups) in the same way as they would access individual workers of
75# the citizen class. In peer-to-peer mode, no group proxy is created. Instead,
76# the group setpoint is changed whenever *any* member's setpoint is changed. In
77# effect, all the group's members behave as though they were group proxies.
78# **Adding Citizens** New citizens may be added to a Grouper instance at any
79# time, using OcaGrouper's **AddCitizen** method. Newly-added citizens are by
80# default not members of any group. Citizens may be enrolled in groups at any
81# time using OcaGrouper's **SetEnrollment** method. **Deleting** The Grouper
82# allows deletion of groups and citizens at any time, although excessive
83# deletion may lead to sparse memory use, depending on Grouper
84# implementation.**Setpoints, Readings, and Aggregation** **Setpoints and
85# Rules** Each group has a **setpoint** (for actuator groups) or **reading**
86# (for sensor groups) whose value is related to its members' setpoints or
87# readings by the combination of two rules:
88#
89# - The group's **saturation rules**, which control handling of overrange
90# conditions; and
91#
92# - Each member's **aggregation rules**, which determine the algorithms by
93# which aggregate values are computed.
94#
95#
96# ** Scope of the OcaGrouper Class** Many aspects of groupers will vary from
97# product to product. **OcaGrouper** is an abstract class that defines common
98# concepts and terms for groupers, a canonical control interface, and most
99# aspects of membership management . However it but stops short of specifying
100# actual semantics. Implementations will need to define (at least):
101#
102# - Saturation rules
103#
104# - Aggregation rules
105#
106# - Error-handling mechanisms (e.g. what happens when a grouper loses its
107# connection to a citizen, and what happens when it later re-attaches)
108#
