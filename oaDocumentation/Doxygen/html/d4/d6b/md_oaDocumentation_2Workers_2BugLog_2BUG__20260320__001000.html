Bug Report: Widgets Using 'widget_type' Not Rendering

Issue

GUI components defined using the widget_type key instead of the standard type key were not rendering in the application. This specifically affected the new black_to_wink_2.json test file and other components like VU_Meter_Knob.json.

Root Cause

The WidgetTypeResolver.resolve_type method was only inspecting the type key in the widget configuration. If type was missing, it returned an empty string. The WidgetSchemaNormalizer then assigned this empty string back to the type key. During the build process, the EngineRenderScheduler would see the empty type and fail to find a corresponding widget creator, silently skipping the widget creation.

Resolution

  1. Modified oaGui/Core/parser/standardizers/widget_type_resolver.py to check both type and widget_type keys during type resolution.
  2. Standardized oaGui/Assets/right_50/bottom_90/9_Zoo/1_buttons/1_Wink/11_black_to_wink_2/black_to_wink_2.json to use the standard type key for all its 100 widgets to ensure maximum compatibility and follow project conventions.

Files Modified

  • oaGui/Core/parser/standardizers/widget_type_resolver.py
  • oaGui/Assets/right_50/bottom_90/9_Zoo/1_buttons/1_Wink/11_black_to_wink_2/black_to_wink_2.json

Verification Evidence

Analysis of the WidgetSchemaNormalizer and EngineRenderScheduler code confirmed the failure path when type was empty. The fix ensures that any widget using widget_type is now correctly identified and its creator method is retrieved.
