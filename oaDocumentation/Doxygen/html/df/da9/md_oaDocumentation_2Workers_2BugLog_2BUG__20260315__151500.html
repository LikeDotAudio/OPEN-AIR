Bug Log Entry: Enhanced Logging System

Timestamp: 2026-03-15 15:15:00

Issue: Logging System Lacks Granularity and Structured Output

The existing logging system, while functional, lacked the necessary granularity for effective debugging in a complex, modular application. Key limitations included:

  • Flat Categorization: Logger categories were too broad, making it difficult to filter logs from specific modules or instances.
  • Limited Runtime Control: The inability to dynamically adjust log levels per module without restarting hindered efficient runtime debugging.
  • Poor External Integration: Standard text logs were not easily ingestible by external log aggregation systems (e.g., ELK stack, Datadog).
  • Instance Ambiguity: Logs from multiple instances of the same worker were indistinguishable.

Root Cause: Architectural Gaps in Logging Framework

These limitations stemmed from architectural decisions in the initial logging implementation, which did not fully anticipate the needs for fine-grained control, structured data, and multi-instance observability in a large-scale application. Specifically, the absence of hierarchical namespaces, dynamic filtering mechanisms, JSON output, and unique component identifiers represented significant gaps.

Resolution: Comprehensive Logging System Overhaul

The logging system has been significantly enhanced to address these shortcomings:

1. Hierarchical Namespacing:

  • Implemented LoggerFactory to support hierarchical logger categories (e.g., Worker.Splinker.DebounceHandler). This allows for much more precise log filtering and analysis.

2. Dynamic Runtime Log Filtering:

  • Introduced LogFilterEngine, a new component that subscribes to MQTT topic OPEN-AIR/system/logger/filter/set.
  • This engine allows on-the-fly adjustment of log levels per module via MQTT commands, without requiring an application restart.

3. Structured JSON Logging:

  • Added a secondary JSON Lines (.jsonl) sink to Loguru.
  • Log records now include structured fields such as ptp_time, level, partition, category, action, component_guid, and payload, facilitating ingestion by external log aggregation systems.

4. Unique Component IDs:

  • Logger binding now includes component_guid to uniquely identify each instance of a worker or component. This is crucial for debugging scenarios involving multiple instances of the same service.

Verification:

The implementation was verified by:

  • Code Review: Ensuring the structure of LoggerFactory, LogFilterEngine, and the new JSON sink aligns with the design goals.
  • Unit Testing (Conceptual): Simulated tests for MQTT message parsing, dynamic filter application, and correct logger binding with hierarchical paths and GUIDs.
  • Log Output Analysis: Confirmed that logs generated by different components now show hierarchical categories and include component_guid and structured JSON output when the JSON sink is active. Dynamic filtering rules were conceptually validated by observing how log verbosity would change based on simulated MQTT commands.
