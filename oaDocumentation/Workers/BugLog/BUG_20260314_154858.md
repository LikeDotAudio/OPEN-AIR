# BUG: Sash Reconfiguration Loop
- **ID**: 20260314_154858
- **STATUS**: RESOLVED
- **SEVERITY**: 2 (High)
- **COMPONENT**: `oaGuiBuild.Managers.engine_gui_display`

## Issue
The application's UI was entering a high-frequency loop, repeatedly enforcing sash positions for `ttk.PanedWindow` widgets. This resulted in significant log spam with the "[LAYOUT]" tag and caused high CPU utilization, leading to a sluggish and potentially unresponsive user interface. The issue was triggered by a recursive feedback loop where the `<Configure>` event binding would re-trigger the sash positioning logic while it was already running.

## Root Cause Analysis
The `configure_sash` function was bound to the paned window's `<Configure>` event. Inside this function, a call to `paned_window.tk.call(..., "sashpos", ...)` would adjust the sash. This adjustment itself would sometimes trigger another `<Configure>` event, causing the function to call itself recursively without any guard, leading to an infinite loop.

## Resolution
A recursion guard was implemented to break the loop.
1.  A boolean attribute (`sash_config_in_progress`) was added to the `paned_window` instance, initialized to `False`.
2.  The `configure_sash` function was modified to check this flag upon entry. If the flag is `True`, the function returns immediately, preventing recursion.
3.  The flag is set to `True` at the beginning of the function's execution.
4.  A `try...finally` block was wrapped around the core logic to ensure the flag is always reset to `False` upon completion, even if an error occurs.

This ensures that even if a `<Configure>` event is fired while the sash is being programmatically positioned, the handler will not execute again until the current execution is complete.

## Verification
The absence of the "[LAYOUT] Sash positions enforced for..." log spam during window resizing confirms the fix. The application's CPU usage remains normal during these operations, and the UI remains responsive.
