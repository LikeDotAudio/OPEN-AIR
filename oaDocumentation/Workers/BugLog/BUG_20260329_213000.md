# Bug Report: BUG_20260329_213000

## Issue
The SNMP bridge exhibited sporadic "flickering" behavior, appearing active and then quickly going offline. This caused inconsistent telemetry and potential resource conflicts.

## Root Cause
The issue was caused by two primary factors:
1.  **Duplicate Initialization**: Both the UI and Core partitions were attempting to start an active SNMP bridge. Since they share the same configuration (binding to port 161), they competed for the same system resources and state files.
2.  **Incomplete Cleanup**: The `SNMPManager.stop()` method did not properly terminate its background worker threads (`SnmpStatePersister` and `SnmpLogMonitor`) or unregister its observer from the `ProtocolRouter`. This left "ghost" bridge activities running after a requested stop or during a restart.

## Resolution
1.  **Partition Awareness**: Updated `oaComProtocols.oaComSNMP/Entry.py` to use `OPEN_AIR_PARTITION_ID`. The SNMP bridge now defaults to `run_bridge=True` only in `CORE` or `STANDALONE` partitions. In the `UI` partition, it defaults to "Observer" mode, which listens to telemetry without attempting to manage the physical SNMP daemon.
2.  **Robust Cleanup**: Enhanced `SNMPManager.stop()` to:
    - Unregister from the `ProtocolRouter` (using a newly added `unregister_cache_observer` API).
    - Signal and join the background worker threads.
3.  **API Symmetery**: Added `unregister_cache_observer` to `ProtocolRouter` to allow transport managers to cleanly detach from the system firehose.

## Verification
1.  Unit tests in `oaComProtocols.oaComSNMP/Tests/test_snmp_manager.py` passed.
2.  Verified that `ProtocolRouter` now correctly handles observer removal.
3.  Log analysis confirms that UI and CORE now have distinct, non-conflicting roles in SNMP management.
